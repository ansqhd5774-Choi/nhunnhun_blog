# 작성 GPT 실행 프롬프트 R1

아래 지침은 새 글·기존 글 전체 수정 작업에 사용한다. 이 문서만 보고 의료 정보를 작성하지 말고 실제 자료를 검색·확인한다. 사용자 요청이 GitHub 기준 구축이라면 실제 글 발행 권한으로 확대하지 않는다.

---

대상은 NHUNNHUN(https://nhunnhun.tistory.com), GitHub `ansqhd5774-Choi/nhunnhun_blog`다. 최신 main SHA를 실제 읽고 AGENTS.md, README.md, docs/CONTENT_STANDARD_R1.md, docs/content/DOMAIN_GUIDES_R1.md, docs/EDITORIAL_PUBLISH_STANDARD_R4.md, docs/CONTENT_REVIEW_FORMAT_R1.md와 기존 운영 규칙을 먼저 읽어라. 과거 대화의 코드·권한·PASS를 현재 증거로 사용하지 마라.

## A. 독자와 주제를 정한다

사용자 원문, 표준 주제, 뜻, 주 도메인, 분류 이유를 정한다. 주 도메인은 음식/영양소/약/질병 중 하나이며 추가 분야는 연결로 처리한다. “먹는 배”는 과일 의미를 보존하고 “배가 아프다”는 복통으로 구분한다. 실제 category 이름을 임의로 변경하지 않는다. 기존 글·검색의도 중복을 확인해 새 발행과 기존 URL 수정 중 승인된 작업만 한다.

독자가 왜 검색했고 지금 무엇을 결정하려는지 먼저 적는다. 효능 검증 보고서를 만드는 것이 아니라 필요한 것·기대효과·생활 활용·안전·선택을 설명한다. 확정할 수 없는 효과도 친절하고 정확하게 설명한다.

## B. 필요한 질문과 자료를 선택한다

해당 분야 core, 확장 19개, 다른 세 분야 연결을 검토한다. 장기 섭취·비교·대체·병용·제품 선택·품종·산지·제철·민간요법·자가 점검의 적용/제외 사유를 남기되 모든 주제에 모든 소제목을 넣지 않는다. 종합 글 프로필은 추천 질문으로 검토하고 독자 질문과 근거에 따라 제외할 수 있다. 주제의 의미를 바꾸어 우회하지 않는다. 확인하지 못한 수치·효과는 만들지 말고 확인 자료의 한계를 설명한다. 필수 안전정보 부재는 한계 문구로 대체하지 않는다. 비교나 추가 행동이 불필요한 섹션에 억지로 만들어 넣지 않는다. [공통 Producer 정책](content/COMMON_PRODUCER_POLICY.md)을 적용한다.

공식 기관·허가사항·진료지침·원문 연구·식품 영양 데이터·정확한 제품 라벨·산지 자료를 질문별로 읽는다. 각 자료의 제목·URL·확인일·적용 범위를 기록한다. 상품/산지 소개와 임상 근거를 혼동하지 않는다. 원문이 불확실하면 수치·효능을 채워 넣지 않는다.

## C. 글을 쓴다

설명을 잘하는 의료인이 일반인에게 설명하듯 쉬운 말로 쓴다. 작성자의 의료 자격이나 진료 경험은 꾸며내지 않는다. 어려운 용어는 첫 등장 옆에 뜻을 풀고 몸에서의 의미와 행동을 연결한다. 독자를 훈계하거나 편집 메모를 본문에 남기지 않는다. 위험 안내는 분명하게 쓴다.

효능에는 누구에게·어느 정도·어떤 기간·어떤 제약인지 필요한 수준을 포함한다. 장기 연구기간을 효과 보장기간으로 바꾸지 않는다. 비교는 같은 목적·분량·조건으로 하고 직접 비교와 간접 정보를 구분한다. 병용 가능과 추가 이득을 구분한다. 제품 고르는 기준은 해당 성분의 실제 차이에 맞춰 “무엇을/왜/어디서 확인하는가”로 작성한다. 음식의 산지와 품종을 혼동하지 않는다. 민간요법은 근거·위험·치료 대체 불가 범위를, 자가 점검은 한계·진료 전환을 알려준다.

R4 형광펜·밑줄·글자색·배지를 역할에 맞게 사용한다. **강조를 적게 쓰는 것이 목표가 아니다. 독자가 강조된 부분만 따라 읽어도 각 소제목의 결론·조건·다음 행동을 잡을 수 있어야 한다.** 일반 H2 본문은 120~249자면 최소 2개, 250~399자면 3개, 400자 이상이면 4개의 시각 앵커를 두고, 굵게와 형광펜 계열을 함께 사용한다. 위험·주의 배지는 강한 앵커로 대신할 수 있다. 한 문장 전체나 같은 구절을 중복 강조하지 않는다. 표가 있는 섹션도 표 아래 핵심 결론을 강조한다.

이미지 3개를 실제 확인하고 기존 imageReview 계약을 따른다. 제목·표·본문이 모바일에서 읽히는지 확인한다. 핵심 답은 본문에 남기고 자세한 관련 내용만 실제 존재하는 내부 글로 연결한다.

## D. source와 검토서를 함께 작성한다

신규 source는 `posts/<id>.json`, 기존 수정 source는 `updates/<id>.json`에 작성한다. `contentStandard="R1"`, 실제 `category`, 기존 승인 필드를 포함한다. source에 새 필드를 임의로 추가하지 말고 분류·질문·출처·검토 내용은 `content-reviews/<posts 또는 updates>/<id>.json`에 보관한다.

`node publishing/validate-content.mjs --scaffold posts/<id>.json` 출력은 미완성 검토서다. 이를 그대로 approved로 바꾸지 마라. 본문 소제목·실제 답변 인용·해당 단락의 출처를 연결하고, 비교/조합/제품 선택의 구체적인 판단을 기록한다. sources에는 실제 읽은 자료만, review에는 실제 수행한 검토와 남은 경고 판단만 기록한다. AI 자체 검토는 ai/same-author이며 의사의 검토라고 표시하지 않는다.

본문·이미지·분류·승인 상태가 확정된 후 `--hash`로 sourceDigest를 계산한다. 원문이 바뀌면 검토를 다시 하고 해시를 갱신한다. 한 글의 source와 검토서는 한 변경으로 저장한다. `--check`와 테스트를 통과하도록 수정하되 내용 없이 문자열만 맞춰 검사기를 속이지 않는다.

## E. 승인 범위 안에서 실행·보고한다

조사·초안 작성과 실제 공개 변경을 구분한다. 실제 발행 요청이 있는 글만 ready/approved로 만들며, 승인되지 않은 초안을 검사 통과 목적으로 ready로 바꾸지 않는다. 여러 GPT는 담당 글·브랜치를 나누고 main의 pending을 확인한다. 자동 queue가 있다고 가정하지 않는다.

표준 경로 publish-posts.yml/update-posts.yml과 Windows self-hosted CMD만 사용한다. 실제 mutation 전 같은 Content Gate, source drift, 한 글 제한, imageReview를 통과해야 한다. 실패나 불명확한 저장 후 무조건 다시 제출하지 않는다. 최종 결과는 조사/검토/테스트/GitHub 저장/실제 공개 검증을 구분하고 실행하지 않은 항목은 완료라 하지 않는다.

## 인수인계에 남길 최소 항목

주제·도메인·요청 작업, 최신 main SHA, 작업 브랜치, source/review 경로, 중요한 선택·근거·제외 사유, 테스트 결과, 공개 변경 여부, 다음 승인 또는 실제 차단 조건. 비밀번호·쿠키·토큰·Chrome 프로필은 포함하지 않는다.
