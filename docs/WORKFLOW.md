# 수정 → 검증 → 백업 → 적용 → 실사이트 검수

0. 요청 대상 URL, 원하는 변화, 금지 사항, 적용 승인 유무를 changes/기록에 작성한다. 최신 관리자 스킨/글 원본과 로컬 기준의 차이를 확인한다. 로그인 필요 시에만 사용자에게 요청하고 비밀번호·OTP를 받거나 기록하지 않는다.
1. 수정: current와 원본을 보존하고 proposals/작업ID/에 후보를 만든다. 스킨 패키지는 전체 파일을 복사하고 CSS 후보를 패키지의 style.css에 반영한다. 인라인 JS는 HTML에 유지한다. SEO·광고·카테고리·글 작업을 한 변경에 임의 혼합하지 않는다.
2. 검증: 원본 대비 변경 차이, HTML 닫힘, 티스토리 치환자, 이미지 경로, JS 오류 가능성을 검사한다. 티스토리 템플릿을 일반 HTML 실행 결과로 대체하지 않는다. 가능하면 관리자 미리보기로 홈·카테고리·글 상세의 PC 1440×900 / 모바일 390×844를 확인하고 메뉴·검색·스크롤·광고 겹침을 검사한다. 미리보기와 운영 증거를 구분한다.
3. 적용 직전 백업: 실제 현재 스킨 ZIP을 새 backup/날짜-작업ID/에 다운로드하고 추출·SHA256·필수 파일 존재를 검사한다. 원본 글은 제목·본문 HTML·카테고리·태그·발행 상태를, 설정 변경은 해당 화면의 이전 값을 민감정보 없이 별도 보존한다. 이전 작업 백업을 최신 백업으로 간주하지 않는다.
4. 적용: 검증 결과, 최신 백업, 복구 경로가 준비되면 승인 범위에서 필요한 파일/설정만 적용한다. 프로젝트 초기 설정 요청만으로 후속 운영 변경을 승인했다고 판단하지 않는다. 글 대량 수정 대신 승인된 한 글 또는 작은 묶음으로 진행한다. 저장 timeout이면 실제 반영 상태부터 확인하며 무조건 재실행하지 않는다.
5. 실사이트 검수: 공개 홈·해당 카테고리·변경 글에서 제목·본문·링크·검색·메뉴·PC/모바일 레이아웃과 콘솔의 새 오류를 확인한다. 광고는 표시·겹침만 관찰하고 절대 클릭하지 않는다. 캐시/로그인 차이는 기록한다. HTTP 200이나 적용 버튼 성공만으로 완료 판정하지 않는다.
6. 성공: 적용된 후보의 해시, 시각, 대상, 스크린샷/관찰 결과를 기록하고 current를 실제 적용 상태와 일치시킨다. 실패: ROLLBACK.md에 따라 변경 범위만 복원하고 공개 화면을 검수한다.

자동화 접근이 막혀도 운영 실패로 쓰지 않는다. 공식 수동 경로가 있다면 목적 → 준비 상태 → 화면 → 클릭 → 입력/실행 → 정확한 횟수 → 기대값 → STOP 조건 → 금지 행동 → 반환 결과 순서로 사용자 안내를 만든다.
