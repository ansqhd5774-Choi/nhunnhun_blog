## 1. 목표: 검색어 설명을 넘어 오늘의 선택을 돕는다

독자는 논문을 검토받으러 온 것이 아니라 건강에 대한 궁금증과 생활 속 선택을 해결하려고 방문한다. 먼저 “왜 이 검색어를 입력했는가, 어떤 상황인가, 무엇을 결정하려는가”를 파악한다. 주제의 장점·현실적인 기대·대상·사용법·위험·대안이 서로 연결되어야 한다. 기대효과가 확인되지 않았다는 답도 유용하다. 이를 무조건 긍정적으로 꾸미거나 결론 없이 경고만 반복하지 않는다.

음식·영양소·약·질병은 독립된 네 개의 목차가 아니라 건강 문제에 접근하는 네 입구다. 감기약 독자는 약 선택뿐 아니라 함께 먹기 편한 식사, 배즙 같은 생활 음식의 의미, 다른 약·영양제 병용, 집에서 할 일과 진료 시점을 함께 궁금해할 수 있다. 다만 “함께 이용할 수 있다”와 “함께 이용하면 효과가 더 좋아진다”는 다른 주장이다.

글을 읽은 독자는 다음을 말할 수 있어야 한다: 무엇인지, 내 상황에 의미가 있는지, 어떤 변화까지 기대하는지, 실제 사용·식사·구매 방법, 피해야 할 선택, 다음 행동. 본문 대신 논문명·숫자·한계·반박을 나열해 독자에게 결론을 떠넘기지 않는다. 반대로 논문이 불확실하면 확실한 효능을 만들어내지 않는다.

## 2. GPT와 자동화의 역할을 구분한다

| --- | --- | --- |
| 작성 GPT | 입력 의미 해석, 분류, 최신 검색, 자료 읽기, 질문 선택, 원고·검토서 작성 | 실제 읽지 않은 출처·보지 않은 이미지 검토 |

검사 PASS는 **선언된 규격과 검토 기록이 일치한다는 뜻**이다. URL의 존재나 문장 길이만으로 정확성을 증명하지 않는다. `semanticVerification=editor-attested-not-automatically-proven`을 유지한다. 검토자가 같은 작성 AI라면 `same-author`로 기록하고 독립 의료 검토로 포장하지 않는다. 자동화를 위한 추가 유료 AI API는 도입하지 않는다.

## 3. 글의 의미와 주 카테고리부터 확정한다

원문 요청, 표준 주제, 의미, 주 도메인, 엔티티 ID, 분류 이유를 보존한다. 예: `먹는 배 글 적어줘` → `topic=배`, `meaning=과일 배`, `domain=food`, `entityId=food:pear`. “먹는 배”를 잘라서 문맥을 버리지 않는다. 복통은 `복통`으로 별도 정규화한다. 모호함을 해소하지 못하면 초안 상태로 두고 공개하지 않는다.

주 도메인은 food / nutrient / medicine / disease 중 하나다. 티스토리 category는 음식 / 영양소 / 실제 약학·약·약약 / 질병과 대조한다. `약약`은 기존 표시명을 검증에서 허용하는 것이며 사이트 이름을 변경하는 것이 아니다. 타 도메인 연결을 추가했다고 주 도메인을 바꾸거나 다른 세 분야의 전체 목차를 강제하지 않는다.

코드에는 명확한 예시의 오분류 방지와 사과·배·수박·비타민C·피크노제놀·감기약·감기의 종합 안내용 추천 프로필이 있다. 모든 세상 주제를 아는 사전은 아니다. 새 주제는 GPT가 근거와 의미를 검토한다. 프로필은 질문 후보이며 적용 강제가 아니다. 독자 질문에 불필요하거나 확인 자료로 답할 수 없는 확장은 구체적 제외 이유를 남긴다. 알려진 주제의 의미·entityId는 그대로 유지한다.

## 4. 고정 목차가 아닌 질문 모듈

`publishing/standards/`에 네 분야의 core와 질문 라이브러리를 둔다. “소제목 46개”를 매번 쓰는 방식이 아니다. 하나의 자연스러운 소제목에서 여러 관련 질문에 답해도 된다. 다만 각 모듈의 실제 답변과 출처를 검토서에서 찾아갈 수 있어야 한다. 본문 제목에 질문만 써놓고 설명이 없으면 통과하지 못한다.

공통 필수 계약은 정체·출처·근거 범위·안전·HTML·최종 검토·중복 제출 방지다. 분야 core는 검토할 질문이지 항상 긍정적 효능이나 숫자를 채워야 하는 요구가 아니다. 수치·효과를 확인하지 못하면 확인한 자료의 한계와 판단 가능한 범위를 실제 본문에서 설명할 수 있다. 확인 자료에 없다는 이유만으로 세상에 근거가 없다고 단정하지 않는다. 의약품 허가·금기나 질병 위험신호 등 필수 안전정보를 확인하지 못한 경우에는 이 방식으로 우회하지 않는다. 확장 질문은 필요성·근거를 확인해 선택하고, 일반 지침은 실제 적용 범위에서 생활 안내로 사용할 수 있으나 개별 효능·용량의 증거로 확대하지 않는다. 상세 자동화 규칙은 [공통 Producer 정책](content/COMMON_PRODUCER_POLICY.md)을 따른다.

## 5. 확장 질문을 깊게 다루는 기준

### 꾸준히 먹거나 사용하면 어떻게 되는가

연구·허가사항의 대상, 형태, 양, 기간, 관찰 지표를 함께 확인한다. 효과 시작 시점, 평가한 시점, 계속 사용할 이유, 장기 안전성 자료, 재평가할 조건을 분리한다. 연구기간이 12주라는 사실을 “12주가 지나면 누구나 체감한다”로 바꾸지 않는다. 1주·1개월·3개월 표를 채우기 위해 없는 변화를 만들지 않는다. 음식에는 전체 식단과 대체한 음식의 영향을, 약에는 질환별 치료기간과 임의 중단 위험을 고려한다. 장기 자료가 부족한 경우 이를 짧게 설명하고 관찰·상담 기준을 제시한다.

### 다른 것과 비교하면 얼마나 나은가

같은 목적·대상·단위·1회량·기간으로 비교한다. 수치 비교는 측정 조건과 기준량을 표 옆에 적는다. 직접 비교시험과 별개 연구의 간접 비교를 구분하며, 서로 다른 연구의 숫자를 빼서 우열이나 “몇 배”를 계산하지 않는다. 비교의 결론은 “누구에게 무엇이 더 맞는가, 서로 대체 가능한 범위는 어디까지인가”다. 효과 외 비용·편의·부작용도 포함한다. 비교가 불가능한 정보는 빈칸을 꾸미지 말고 이유를 밝힌다.

### 같이 먹거나 사용하면 좋은가

추가 효능, 흡수·영양 보완, 증상을 덜어주는 보조 식사, 병용 가능만 확인된 경우, 주의·금기, 근거 부족을 구분한다. 조합을 권할 때는 누구에게 어떤 이점인지와 과다·중복·상호작용을 같이 확인한다. 원리만 비슷하다는 이유로 상승효과를 만들지 않는다. “공복을 피하면 먹기 편하다”는 설명을 약효 증가로 바꾸지 않는다. 약 복용 시간·간격은 정확한 제품의 허가사항이나 근거를 확인해 쓴다.

### 어떤 제품·대체품을 선택할까

“좋은 브랜드를 사세요”로 끝내지 않는다. 해당 성분에서 실제 차이가 나는 기준을 조사해 선택 기준·중요한 이유·라벨에서 확인할 위치를 연결한다. 용량 표시는 1정/1회/하루, 원료 총량/유효성분량을 구분한다. 비싼 제형의 혈중 수치 차이와 실제 건강상 이점은 다른 질문이다. 가격 비교에는 판매처·확인일·1일 또는 동일 분량 기준을 남긴다. 광고·제휴 여부를 숨기지 않고, 순위·판매량을 효능 증거로 쓰지 않는다. 처방약을 쇼핑상품처럼 순위화하거나 독자에게 임의 교체하도록 지시하지 않는다.

### 품종·지역·제철은 어떻게 다를까

사과처럼 산지와 품종 선택이 중요한 음식은 맛·신맛·향·단단함·용도·수확 시기·저장 상태를 비교한다. 같은 산지라도 품종·농장·해당 연도·수확일·저장 조건이 다를 수 있다. 지자체 소개는 산지 특성을 설명하는 자료이지 전국 우열이나 건강효과를 입증하는 자료가 아니다. 브릭스 숫자에는 품종·측정 조건을 붙인다. 특정 지역이 더 건강에 좋다고 확대하지 않는다.

### 민간요법과 자가 점검

독자가 실제 찾는 민간요법을 외면하지 않되 도움 가능성·증거·위험·표준치료와의 관계를 설명한다. 안전한 생활관리와 근거 없는 치료 주장을 구분하고, 위험한 방법의 실행 절차를 제공하지 않는다. 음식의 편안함을 치료효과로 바꾸지 않는다. 자가 점검은 관찰할 증상·기간·변화와 진료 전환을 돕는 용도다. 검증되지 않은 점수표·확률로 질병을 확진하지 않는다. 유효한 도구를 인용할 때는 대상·해석 한계·출처를 붙인다. 응급신호가 핵심인 질병은 긴 설명보다 먼저 행동을 안내한다.

## 6. 다른 세 분야와 연결한다

각 연결은 `included` 또는 `not-applicable`과 구체적인 이유로 기록한다. 포함하는 연결에는 실제 본문 답변·관계 종류·출처가 있어야 한다. “질병도 중요합니다” 같은 이름만 등장하는 문장은 연결이 아니다. 반대로 근거 없는 병용 추천이나 드문 위험을 억지로 넣어 네 분야를 채우지 않는다.

본문 안에서 당장 필요한 답을 먼저 주고, 자세한 내용은 실제 존재하는 관련 글로 연결한다. 내부링크로 이동해야만 필수 안전정보를 알 수 있도록 숨기지 않는다. 관련 글 URL·내용을 실제 확인하며 없는 글·잘못된 숫자 URL은 만들지 않는다. 외부 근거 링크와 내부 이동 링크의 목적을 구분한다.

## 7. 문체: 쉽고 존중하는 설명

어려운 말은 필요할 때만 쓰고 처음 나올 때 바로 풀어준다. `전문용어 → 쉬운 뜻 → 내 몸에서의 의미 → 다음 행동`을 기본으로 한다. “어려우니 몰라도 됩니다”, “상식입니다”, “그것도 모르세요” 같은 태도와 “기존 표현은 삭제하는 것이 맞습니다” 같은 편집 메모는 공개 본문에 넣지 않는다.

좋은 점을 말할 때는 조건을 함께 전달하고, 근거가 부족하면 이해할 수 있는 판단으로 마무리한다. 부정문을 없애려다가 위험을 흐리거나 효과를 부풀리지 않는다. 금기·중복복용·응급상황의 지시는 명확해도 된다. 독자가 약 이름만 안다고 해서 어리석게 보거나 걱정을 사소하게 취급하지 않는다. 실제 의료인이 아닌 작성자에게 진료 경험·전문 자격을 부여하지 않는다.

긴 문단·반복·부정적 리듬은 자동 경고 후 편집 검토 대상으로 둔다. 단어 개수가 독자 만족을 측정하는 척도는 아니다. 문장마다 “다만, 아닙니다, 근거 부족”을 반복하지 말고 효능 설명마다 필요한 한계를 모아 독자가 행동할 수 있게 정리한다.

## 8. 근거·안전·최신성

약은 국내 식약처의 해당 제품/성분 허가사항을 우선하고 투여 경로·함량·연령을 일치시킨다. 질병은 국내외 정부·전문기관·진료지침과 원문 연구를 확인한다. 식품은 영양성분 데이터의 기준량·가식부·조리 상태를, 영양소는 필수영양소 권장량/상한과 개별인정 원료의 일일섭취량을 구분한다. 건강기능식품 기능성 인정과 질병 치료 효능은 구분한다.

자료는 주장별로 역할을 나눈다: 건강·안전·영양·허가 / 제품 구성 / 산지 / 맥락. 제조사·지역 홍보·기사·이미지 설명을 임상효과의 독립 증거처럼 쓰지 않는다. 가능하면 원문과 상위 수준 근거를 확인한다. 인용한 수치에는 대상·효과 크기·기간·제약을 알기 쉽게 적는다. 원문을 직접 읽은 날짜와 자료 자체의 발행일은 다르다. 최신성 제목에 연도만 자동 갱신하지 않는다.

건강 근거 최소 2개는 출발점이며 충분한 정확성을 보장하는 개수는 아니다. 이미지 출처만 두 개를 넣어 충족시키지 않는다. 핵심 주장 옆에 해당 근거가 있어야 하며 맨 아래 자료 출처도 정리한다. 읽지 않은 논문, 만들어낸 인용, 근거 없는 수치·효능 순위·자가 점수표·기간별 효과는 금지한다. 개인별 진단·처방 변경·일률적인 중단 지시를 하지 않는다.

## 9. 강조·이미지·모바일

[Editorial R4](EDITORIAL_PUBLISH_STANDARD_R4.md)를 적용한다. 굵게는 핵심 사실, 밑줄은 짧은 비교 차이, 형광펜은 의미에 맞는 핵심 구절, 위험 안내는 글자로 구분되는 배지를 쓴다. 색만으로 의미를 전달하지 않는다. 효과가 불확실한 정보를 초록색 확정 추천처럼 보이게 하지 않는다.

대표 이미지와 서로 다른 이미지 최소 3개, 실제 시각 확인·alt·원출처·사용허가 확인 등 기존 Image Review Gate는 유지한다. 의미 없는 이미지를 수량 때문에 넣지 않는다. 음식은 주제가 실제로 잘 보이는 이미지를, 약·질병은 제품 또는 설명에 맞는 안전하고 정확한 시각자료를 선택한다. 상업제품 이미지의 이용권한도 확인한다. 기존 Commons 전용 계약 변경은 별도 구현·테스트 없이 우회하지 않는다.

표는 단위·조건을 명확히 하고 좁은 화면에서는 표 컨테이너만 가로 스크롤되어야 한다. PC와 모바일에서 소제목·핵심 숫자·주의 배지가 구분되는지 확인한다. 로컬 미리보기 성공과 티스토리 실제 공개 화면 검증은 별도다.

## 10. 실제 작성·검증·발행 절차

1. 최신 main, 운영 상태, 기존 검색의도 중복을 확인한다. 이 문서와 해당 분야 지침을 읽는다.
2. GPT가 입력 의미·주 도메인·독자 상황을 정하고 core와 확장 19개, 다른 세 분야를 검토한다.
3. 공식 자료·원문·실제 제품 또는 산지 차이를 조사한다. 관련 없는 내용은 이유를 남기고 제외한다.
4. 독자 질문 순서로 글을 작성한다. 해당되지 않는 결핍증·섭취량·장기 효과를 채워 넣지 않는다.
5. source에 `contentStandard: "R1"`과 실제 category를 넣는다. 수정 source에도 category를 넣되 공개 분류를 변경하지 않는다.
6. 같은 id의 검토서를 `content-reviews/posts/` 또는 `content-reviews/updates/`에 작성한다. 본문 위치·답변 인용·출처·제품 비교·연결·문체·이미지 검토를 기록한다.
7. 검토 후 최종 source hash를 계산하고 승인 상태를 일치시킨다. 본문·이미지·분류·ready 상태가 바뀌면 검토 해시도 새 검토 후 갱신한다.
8. `node publishing/validate-content.mjs --check posts/<id>.json` 또는 `updates/<id>.json`, `npm test`로 확인한다. 렌더 미리보기도 확인한다.
9. 실제 발행 요청이 있을 때만 source와 검토서를 함께 저장하고 기존 표준 발행/수정 경로를 사용한다. 한 번에 pending 1개와 명시적 승인·source drift·checkpoint를 유지한다.
10. 실제 공개 변경이 일어난 경우에만 익명 전체 본문·이미지·강조·PC·모바일·ledger 검증 후 발행 완료라고 보고한다.

명령과 검토서 상세는 [CONTENT_REVIEW_FORMAT_R1.md](CONTENT_REVIEW_FORMAT_R1.md), 작성 GPT 프롬프트는 [CONTENT_WRITER_PROMPT_R1.md](CONTENT_WRITER_PROMPT_R1.md)를 따른다.

## 11. 병렬 작업·기존 글·한계

여러 GPT가 조사·작성하는 것은 가능하나 글별 브랜치와 담당 파일을 분리한다. `ready` 글 여러 개를 동시에 main에 넣으면 기존 한 건 처리 보호가 중단한다. 이 변경은 자동 대기열 처리 기능을 새로 만든 것이 아니다. 신규 발행과 기존 수정은 같은 브라우저 mutex를 공유한다. GitHub concurrency는 글 대기열 자체가 아니다.

`--all`은 기존 변경 없는 R3 source를 legacy로 보고 보존한다. `--changed`는 새로 작성·수정한 ready source에 R1을 요구한다. 최종 publish/update의 eligible 대상에도 같은 검사를 실행하므로 오래된 미검토 pending을 수동 실행으로 우회할 수 없다. 과거 글을 수정하려면 내용을 실제 검토한 R1 source·review로 준비한다. 기존 published/updated ledger는 소급 재작성하지 않는다.

새 편집 글자 수 하한·상한이나 유용성 비율은 정하지 않는다. 기존 신규 source의 **HTML 200,000자 안전 한도**는 유지되며 독자에게 보이는 본문 글자 수 목표가 아니다. 한계를 이유로 억지 분량을 채우거나 중요한 내용을 빼지 않는다.
