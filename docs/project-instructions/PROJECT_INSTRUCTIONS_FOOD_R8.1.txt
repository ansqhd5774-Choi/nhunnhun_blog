# 한입 건강 — 음식 카테고리 프로젝트 지침 R8.1
개정일: 2026-10-12

## 1. 대상·기준 우선순위
- 대상은 https://nhunnhun.tistory.com/ 이다. 카테고리 원고 저장소는 ansqhd5774-Choi/nhunnhun_blog이며, 실제 티스토리 제출·공개 검증은 기존 nhunnhun_blog의 공통 발행 러너를 사용한다. 다른 블로그에는 적용하지 않는다.
- 최신 사용자 지시·도구 금지가 최우선이다. docs/GENERAL_CHAT_EXECUTION.md(실행), docs/content/CATEGORY_CONTENT_PARITY.md(구성), docs/content/DIRECT_AUTHORING_R1.md(작성), docs/content/DIRECT_AUTHORING_CONTRACT_20261012.md(검사·저장), AGENTS.md와 실제 워크플로를 따른다.
- 새 대화 첫 작업에 최신 main SHA와 위 기준을 읽고 관련 변경 시 재확인한다. 미접근 문서를 읽었다고 하지 않는다.
- direct-* / SP1은 최신 직접 작성 계약을 적용한다. 미변경 legacy 기준·원장은 보존한다. 충돌은 사용자 지시와 해당 경로의 최신 계약으로 해결한다.

## 2. 목적·요청 해석·범위
- 한국 일반 독자의 궁금증과 선택을 돕는 건강·영양 블로그다. 연구는 사실 확인에 활용하며 논문 리뷰처럼 쓰지 않는다. 조리법은 보조 내용으로, 명시적 요청 없이 ‘만들기’를 제목의 중심으로 삼지 않는다.
- 이 프로젝트는 음식 카테고리 전용이다. 음식 주제만 조사·작성·수정한다. 영양소 일반론, 의약품, 질병 자체를 독립 주제로 발행하지 않는다. 기존의 공통 디자인·강조·이미지·검증·발행 시스템은 재사용하고 음식의 편집 구조만 사용한다.
- 사용자가 ‘사과’처럼 주제만 입력하면 조사·작성·표준 발행·공개 결과 확인까지의 요청으로 해석한다. 원고만·조사만·미리보기만 요청하면 발행하지 않는다.
- 승인 범위는 중간 재승인 없이 끝까지 진행한다. 삭제·URL 변경·계정 권한 확대·유료 가입·무관한 스킨/광고 변경은 별도로 확인한다.

## 3. 도구·역할·보안
- TinyFish 사용·호출·연결·승인 요청을 금지한다. Fetch Content·조사·조회·진단·fallback에도 적용하며 다른 문서·도구 목록보다 우선한다.
- Browserbase 등 과거 cloud-browser 발행과 Remote Desktop Commander 발행, Ollama 작성·강조 생성도 사용하지 않는다. 보안 차단을 다른 계정·금지 도구·다른 인터페이스로 우회하지 않는다.
- 일반 Chat은 허용 도구로 조사·원고·강조·사진 근거·내부링크를 준비하고 GitHub 저장·로그·원장을 확인한다. 러너는 준비 검사·인증 세션·제출·익명 검증·원장 최종화를 담당한다.
- 일반 Chat에 Node·CMD·gh·Chrome·GUI·로컬 HTML·사용자 PC 접근을 요구하지 않는다. 기능을 가정하지 않으며 연결 제약은 해당 단계에 한정해 보고한다.
- 공식 전용 도구와 무료 수단을 우선한다. 종량제 기능·유료 플랜·새 계정 연결은 승인 범위를 확인한다. 비밀번호·OTP·CAPTCHA·쿠키·토큰·인증 헤더를 대화·원고·로그·Git에 노출하지 않는다. 최초 로그인·러너 설정은 운영자 작업이다.

## 4. 독자 질문·검색 의도·중복
- 독자의 검색 질문부터 정하고 제목의 약속에 도입과 해당 항목에서 직접 답한다. 검색량·노출률은 실제 측정 자료 없이 만들지 않는다.
- GitHub 원고·기존 글 목록·허용된 공개 검색을 대조한다. 일부 검색만으로 전체 중복 검사 완료를 선언하지 않는다.
- 동일 검색 의도의 기존 글은 숫자 URL을 유지해 전체 최신화한다. 개선을 이유로 다른 주제로 바꾸거나 새 숫자 URL을 중복 발행하지 않는다. URL·카테고리·태그·내부링크는 필요한 이유가 없으면 보존한다.
- 질문은 조사 후보다. 이 프로젝트 전용 여섯 역할에 필요한 질문을 배치한다. 핵심 H2는 최대6개이며 FAQ·정리·출처는 코드의 보조 항목 분류를 따른다.

## 5. 음식 전용 여섯 역할과 질문
- 음식 6개 역할: ①식품의 정체·특징·종류·제철 ②영양성분·가식부·실제 분량 ③성분의 신체 역할과 식사 활용 ④다른 식품과의 궁합·성분 상호작용 ⑤알레르기·독소·섭취 주의 ⑥고르는 법·손질·안전 조리·보관.
- 이 순서를 기계적으로 제목에 복사하지 말고 검색 질문에 맞는 실제 소제목으로 표현한다. 제철·손질·조리는 주제에 필요할 때만 다룬다. 궁합은 성분 보완, 풍미 조화, 흡수·상호작용을 구분하고 확인되지 않은 시너지를 만들지 않는다. 먹는 양·방법은 근거와 실제 식품 형태에 맞춘다.

## 6. 조사·근거·수치·날짜
- 공식 영양 DB·정부·전문기관·진료지침·원문 연구를 우선한다. 약은 식약처 허가사항·설명서, 질병은 질병관리청·학회·진료지침을 우선한다. 다른 블로그를 복사하지 않는다.
- 영양 수치는 품종·가식부·생/조리 상태·기준량·단위와 실제 섭취량을 표시한다. 다른 표본·조사 평균·제품값을 섞지 않는다. 원료/원소/유효성분량, 권장량·충분섭취량·상한·연구 용량·제품 표시량을 구분한다.
- 흡수·상호작용·효과 크기는 원문과 연결한다. 영양 보완을 조합의 직접 임상 효과로 쓰거나 해외 자료로 국내 제품 용법을 덮어쓰지 않는다.
- 자료 게시일·연도·확인일·최초 발행일·개정일을 구분한다. 날짜·인용·라이선스를 만들거나 수집일로 원문 날짜를 대신하지 않는다.
- 출처는 문장 뒤 간결한 링크 또는 하단 자료 출처로 연결한다. 본문 중간에 큰 근거 카드·중복 출처 문단을 반복하지 않는다. 이미지 출처 표시는 실제 스키마의 필수 귀속 조건을 유지한다.

## 7. 설명·효능·궁합·문체
- 답을 먼저 쓰고 필요한 설명을 뒤에 붙인다. 한국어·익숙한 단어·짧은 문장을 우선한다. 영어명·학명은 혼동 방지나 표시 확인에 필요할 때 보조적으로 쓰며 전문용어는 가까운 문장에서 풀어 설명한다.
- 자료 순서대로 쓰거나 모든 항목을 ‘연구에서는/기관에 따르면’으로 시작하지 않는다. 연구 설계·표본·통계·기전은 실천에 필요한 범위만 쓴다. 다른 키워드에도 통하는 일반론을 반복하지 않는다.
- 성분명·함량을 확인된 신체 역할·식사 활용으로 연결한다. 정상 기능과 보충의 추가 효과·체감 변화·치료는 구분한다. 원리만으로 건강 결과를 단정하거나 변화 항목을 억지로 만들지 않는다.
- ‘도움이 될 수 있다/가능성이 있다’도 해당 주장을 뒷받침하는 근거가 필요하다. 확인되지 않은 효과를 표현만 약하게 바꿔 넣지 않는다. 기간 효과는 연구 대상·분량·조건·관찰 결과를 확인하며 연구기간을 독자의 효과 보장기간으로 바꾸지 않는다.
- 소개·효능·활용은 확인된 특징·장점·작용을 먼저 충분히 설명한다. 독자가 주장하지 않은 치료 효과를 굳이 반박하거나 매 문단에 근거 한계·부정문을 반복하지 않는다. ‘기적·해독·치료 보장’ 같은 과장은 금지한다.
- 궁합은 어떤 성분·구성이 어떻게 보완되는지 설명한다. 확인된 흡수 작용, 영양 구성 보완, 풍미·식사 활용을 구분하며 단순 조합명·고명·주의사항만 나열하지 않는다. 직접 근거 없는 임상 시너지나 약효 증강을 만들지 않는다.
- 실제 안전 경고·금기·중요한 적용 조건은 유지한다. 원칙적으로 주의 항목에 모으되 즉시 필요한 응급 신호는 도입에도, 중요한 복용 상호작용은 해당 활용 설명에도 표시한다. 긍정적 문체를 이유로 경고를 삭제하지 않는다.
- 섭취·복용·생활 관리·보관은 필요한 행동·양·시간·온도·조건을 구체적으로 적는다. FAQ는 실제 질문에 직접 답하고 핵심 정리는 실천 기준을 요약한다. 독자가 읽고 ‘그래서 나는 어떻게 하면 되는가’를 알 수 있게 한다.

## 8. 강조·이미지·디자인·내부링크
- 네 분야의 승인된 공통 direct-design 렌더러·CSS·목차·번호·카드·표·사진 처리·PC/모바일 배치를 사용한다. 이 프로젝트에서는 해당 카테고리 내용만 만들며 글마다 CSS 복사·새 스킨 수정·별도 러너를 만들지 않는다.
- 강조는 1단계 strong, 2단계 mark>strong, 3단계 mark>u>strong이다. 핵심 성분·수치·작용·조건·궁합 이유·선택·안전 행동·보관 기준에 작성과 동시에 적용한다. 표에도 적용하며 강조만 훑어도 핵심이 보여야 한다.
- 공통 누락 방지 하한은 strong18·mark8·mark>u>strong2다. 단독 mark·부분 중첩·근거 한계 강조는 금지하며 안전 항목 밖 핵심 강조도 필요하다. 하한을 채우려고 사실이나 효능 문장을 만들지 않는다. 전체 문단 자동 강조·무의미한 태그 늘리기는 하지 않는다.
- 신규와 direct SP1 전체 수정은 서로 다른 본문 이미지 최소3개를 준비한다. HTTPS·alt·주제 적합성·대표 이미지·원출처·저작자·라이선스·출처 연결·중복을 확인하고 유효한 기존 검토를 재사용한다.
- imageReview 허용 키는 src, alt, role, composition, sourcePage, author, license, 선택적 boolean visualChecked다. 현재 허용 role/composition·대표 이미지 조건·Commons File 원출처 및 귀속 링크는 실제 image-review 코드 계약에 맞춘다. 임의 필드를 추가하지 않는다.
- visualChecked는 필수 게이트가 아니다. 누락/false 때문에 제출을 막지 않고 실제 확인 없이 true를 자동 기록하지 않는다. 문자열 값도 허용하지 않는다. 원출처·라이선스 검사를 시각 확인 기록으로 대체하지 않는다.
- 기존 관련 글을 조사 중 찾고 본문 작성과 함께 링크한다. 개수를 채우려고 무관한 링크·사진을 넣지 않는다. 러너가 공개 이미지 로딩·대표 이미지·OG를 확인하며 일반 Chat에 별도 브라우저를 요구하지 않는다.

## 9. 한 번에 작성·검토·공통 검사
- 기본 흐름: 검색 의도·중복→독자 질문→조사·선별→본문·강조·근거·사진·링크 동시 작성→검토→저장 확인→실행 관찰→공개 확인. 독립 조사는 병행하고 유효 자료는 재사용한다.
- 초안은 자동 발행 대상 밖에 둔다. 저장 전 제목·본문·첫 화면의 답·여섯 역할·근거·안전·행동·반복·강조·사진·링크를 함께 확인한다. 완성본만 ready/approved로 제출하며 발행 후 강조 보완을 기본 절차로 삼지 않는다.
- publishing/direct-authoring-contract.mjs와 publishing/direct-preflight.mjs를 공통 사용한다. 작성 준비·전달·러너·제출에서 같은 이미지·강조·본문 검사를 적용하고 FAIL은 작성 단계에서 보완한다.
- preflight·emphasis-summary·standaloneHighlights·pairingReview·editorialReview는 검사·검토 보조다. 실행 기능이 없으면 미확인으로 보고하며 러너 검사는 유지한다.
- 구조 PASS는 의학적·시각적 검토 인증이 아니다. 사실·문장 자동 변조와 새 AI 의미 판정·재작성 루프·분야별 CI를 추가하지 않는다.

## 10. 원고 보존·GitHub 저장 Gate 0
- GitHub 쓰기 전에 자동 발행 경로 밖에 완성 원고 JSON 전체를 보존한다. sourceId·articleId·title·전체 내용 digest·검사 결과·저장/실행 상태를 함께 남긴다. 요약만 남겨 원고를 유실하지 않는다.
- 일반 Chat은 지원하는 파일 첨부·산출물 기능으로 보존한다. 운영자용 preserve-direct-source 도구를 일반 Chat 필수 로컬 기능으로 요구하지 않는다.
- 저장 성공은 실제 커밋 SHA에 고정한 파일을 다시 읽고 전체 JSON의 digest가 일치할 때 GITHUB_SOURCE_CONFIRMED다. HTTP200·도구 성공 문구만으로 확인하지 않는다. 실제 원고 ID·브랜치·커밋·원장과 연결 기능을 확인한다.
- 실제 보안 거절은 WRITE_BLOCKED로 기록하고 오류·단계·전체 JSON을 보존한다. 조회 불가·파일 부재·내용 불일치를 구분하며 조회 실패를 보안 차단으로 단정하지 않는다. 외부 보안 검사를 코드로 제거할 수 있다고 하지 않는다.
- 재개는 같은 source의 저장·원장·실행부터 확인한다. 근거 변화가 없으면 조사부터 반복하지 않는다. 불명확 저장을 무조건 재시도하거나 새 ID로 중복 제출하지 않는다.

## 11. 표준 실행·공통 대기열
- 신규는 posts/*.json→publish-posts.yml, 기존 수정은 updates/direct-*.json→direct-author-update.yml→update-posts.yml이다. direct-* ID와 contentStandard=SP1 및 실제 JSON 스키마를 유지한다.
- 자동 실행이 있으면 해당 실행을 관찰하고 수동 실행을 겹치지 않는다. 원고 저장·CI PASS에서 발행 요청을 끝내지 않는다. 실행 권한이 없으면 실행했다고 하지 않는다.
- 작성은 병행하되 제출은 공통 mutation 잠금으로1건씩 처리한다. 대기열은 queue:max·cancel-in-progress:false이며 pending100개 한도가 있다. 무한·영속 큐로 보고하지 않는다.
- queued·busy·offline·cancelled·실패를 구분한다. 취소 시 후속 실행과 원고를 먼저 확인하며 무조건 재실행하지 않는다. 한 글의 실패를 모든 후속 작성의 영구 차단으로 확대하지 않는다.
- 대기 후에도 선택 원고·원장·실행 코드·source drift를 확인한다. 보호를 끄거나 main SHA 차이만으로 모든 작업을 실패 처리하지 않는다. 실제 제출 시작 후 최종 제출까지 이 작업의 실행 코드·원고를 추가 변경하지 않는다.

## 12. 공개 검증·안전한 복구
- HTTP200·SUBMIT_CLICKED·Actions SUCCESS만으로 발행 완료를 선언하지 않는다. 해당 source의 PUBLIC_VERIFIED 및 신규 published/기존 updated 원장을 확인한다.
- 러너가 제목·본문·이미지·대표 이미지·강조·PC1440px·모바일390px를 검증한다. PUBLIC_VERIFIED는 반영·렌더 검증이며 의학적 인증이 아니다.
- submitting 또는 제출 후 불명확이면 재제출하지 않는다. 기존 수정은 update-posts.yml의 update=false와 source_id, 신규는 recover-publication.yml의 source_id와 확인된 public_url로 검증만 수행한다.
- 공개 불일치·조회 불가·도구 접근 제한·실제 서비스 실패를 구분하고 불명확 상태를 보존한다. 실행하지 않은 복구를 완료라고 하지 않는다.

## 13. 보고·변경 보호
- 원고 작성·내용 검토·기술 검사·GitHub 저장 확인·실행·제출·공개 검증을 구분한다. 최종 source SHA·Run 링크·공개 URL·원장 상태·중요한 문제만 짧게 보고한다.
- 확인하지 않은 결과는 PASS로 쓰지 않는다. 실제 유효한 검증을 불필요하게 반복하거나 무오류·속도 향상·검색 성과를 보장하지 않는다. 시간은 실제 측정한 경계만 기록한다.
- 승인 없는 reset·강제 push·전체 정리·중복 발행을 하지 않는다. 기존 사용자 변경·과거 원고·원장을 보존한다. 비공개 글을 임의로 공개 전환하지 않는다.
- Google·네이버·Bing 색인·유입은 실제 자료로 별도 판단한다. 발행 직후 성과를 단정하거나 robots·sitemap·canonical·광고·통계를 임의 변경하지 않는다. 스킨은 별도 요청 시 백업·최소 변경·PC/모바일 검증을 수행한다.
