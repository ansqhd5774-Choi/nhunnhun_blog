# 음식 direct/SP1 직접 작성 기술 기준 — 2026-10-15

공유 렌더링·강조·이미지·제출·검증의 기술 계약은 [CATEGORY_CONTENT_PARITY.md](CATEGORY_CONTENT_PARITY.md)를 참조한다. 음식 내용·소제목·문체는 `docs/project-instructions/PROJECT_INSTRUCTIONS_FOOD_R8.1.txt`와 `FOOD_CONTENT_QUALITY_R1.md`만 결정한다.

## 음식 편집 기준 격리
- 음식 원고의 H2·질문·문체·장점·궁합·주의·보관 구조를 만들 때 다른 저장소·다른 카테고리·legacy 공통 문서의 편집 예시를 사용하지 않는다.
- 공통 direct/SP1 코드·테스트에 영양소·약학·질병용 예시가 있어도 음식 편집 기준으로 사용하지 않는다.
- 음식 source의 작성 준비 결과는 `scope=FOOD_ONLY`를 유지한다.
- 음식의 핵심 H2는 사용자 확정 6개 소제목을 그대로 사용한다: 소개 / 영양소·핵심 성분 / 꾸준 섭취 변화 / 궁합·시너지 / 주의사항 / 고르는 법·보관법.
- 음식 원고 작성·수정은 direct/SP1 경로만 사용하고 Queue/Ollama 작성 경로는 사용하지 않는다.

## 역할
- 일반 Chat: 조사, 음식 원고 작성, 쉬운말 편집, 강조, 사진 근거, 내부링크 준비, GitHub 저장 및 실행·원장 확인.
- 공통 러너: preflight, 인증 세션, 티스토리 제출, 익명 공개 검증, 원장 최종화.
- 일반 Chat에 Node·CMD·gh·Chrome·GUI·로컬 HTML·사용자 PC 접근을 요구하지 않는다.
- TinyFish, Browserbase cloud-browser 발행, Remote Desktop Commander 발행, Ollama 작성·강조 생성은 사용하지 않는다.

## 작성 순서
1. 음식 전용 프로젝트 지침과 최신 사용자 지시를 확인한다.
2. 신규 가능성이 있으면 target-resolution 결과를 먼저 확인하고 기존 후보면 숫자 URL 수정으로 전환한다.
3. 검색 의도와 기존 음식 글 중복을 확인한다.
4. 일반 독자의 실제 질문을 정한다.
5. 우수 음식·건강 콘텐츠를 벤치마크해 빠진 생활정보를 확인한다.
6. 맛·식감·종류·영양·활용·궁합·주의·구매·보관 정보를 폭넓게 조사한다.
7. 본문에 사용할 사실과 수치는 작성 전에 확인하되, 확인 과정 자체를 독자용 본문으로 옮기지 않는다.
8. 사용자 확정 6개 소제목으로 본문·강조·사진·내부링크를 완성한다.
9. 정보 중복·부정 과잉·단순 산술 표·쉬운말·안전·이미지·강조를 한 번에 검토한다.
10. Gate 0 보존 후 GitHub에 완성 source만 저장하고 자동 실행을 관찰해 PUBLIC_VERIFIED와 원장 상태까지 확인한다.

## 음식 본문
- 일반 독자가 바로 이해할 답을 먼저 쓴다.
- 글의 중심은 음식의 특징·영양·장점·실제 활용·섭취·선택·보관이다.
- 기관명·DB명·논문명·검토 과정·전문 방법명은 독자 판단에 필요하지 않으면 본문에서 빼고 자료 출처에 둔다.
- 확인해서 사용할 수 없는 내용은 생략하고 독자에게 필요한 다른 생활정보를 더 조사한다.
- 실제 알레르기·독성·금기·중요한 상호작용·응급 행동은 주의사항에서 분명하게 유지한다.
- 주의사항이 소개·영양·꾸준 섭취 변화·궁합을 반복적으로 침범하지 않게 한다.

## 자료 출처 표시 — direct/SP1 활성 규칙
- 본문 문장 사이에 외부 URL을 반복 삽입하지 않는다.
- 필요한 문장 뒤에는 `[1]`, `[2]` 같은 짧은 숫자 주석을 사용한다.
- 실제 외부 URL·기관명·문서명은 글 하단 `<h2>자료 출처</h2>`에 모은다.
- 같은 출처 URL을 하단에서 중복하지 않는다.
- 내부링크는 독자의 추가 읽기를 위한 탐색 링크이므로 본문에 둘 수 있다.
- 사진 원출처·저작자·라이선스도 하단 자료 출처에 모은다.
- legacy `CONTENT_REVIEW_FORMAT_R1.md`의 섹션별 URL 규칙을 음식 direct/SP1 본문 표시 규칙으로 가져오지 않는다.

## 음식 궁합·시너지
- `무엇과 먹으면 좋은가 → 왜 좋은가 → 실제로 어떻게 먹나` 순서로 설명한다.
- 영양 보완, 흡수 도움, 맛·향·식감 조합을 구분해 일반 독자가 이해하기 쉽게 설명한다.
- 확인해서 사용할 수 없는 치료·예방 주장은 조합의 시너지로 만들지 않는다.
- 조합 개수를 맞추기 위해 억지 조합을 만들지 않는다.

## 강조
- 1단계 `<strong>`
- 2단계 `<mark data-tone="..."><strong>`
- 3단계 `<mark data-tone="..."><u><strong>`
- 음식 direct/SP1 하한: strong25, mark12, mark>u>strong8.
- 개수를 맞추기 위해 사실·효능·문장을 만들거나 전체 문단을 자동 강조하지 않는다.
- 강조 우선순위는 음식의 핵심 장점 → 중요한 영양소·성분 역할 → 실제 섭취 행동 → 좋은 궁합 → 구매·보관 기준 → 꼭 필요한 안전 행동이다.
- 단순 계산값·반복 수치·부정 문장·검토용 표현을 강조 개수 채우기용으로 사용하지 않는다.
- 기본 `<mark>`: 노랑 — 핵심 사실·수치.
- `data-tone="positive"`: 초록 — 확인된 긍정적 장점·도움이 되는 실천 행동.
- `data-tone="info"`: 파랑 — 이해에 필요한 기준·비교·섭취/보관 정보.
- `data-tone="caution"`: 주황 — 주의가 필요한 조건·상호작용·오해 방지.
- `data-tone="negative"`: 빨강 — 금기·위험·즉시 피해야 할 행동.

## 이미지
- 신규 및 direct/SP1 전체 수정은 서로 다른 본문 이미지 최소 3개를 준비한다.
- 대표 이미지와 본문 이미지의 src/alt 및 원출처·저작자·라이선스를 확인한다.
- `imageReview` 허용 키는 `src, alt, role, composition, sourcePage, author, license`와 선택적 boolean `visualChecked`다.
- `visualChecked`는 실제 확인한 경우에만 true로 기록하며 필수 게이트가 아니다.
- `imageReview.sourcePage`는 본문 자료 출처에도 같은 HTTPS 링크로 한 번씩 연결한다.

## 저장 전 내용 검토
- 사용자 확정 6개 소제목의 이름·순서·의미를 유지했는가.
- 각 H2 첫 문장이 독자의 질문에 바로 답하는가.
- 글의 대부분이 특징·영양·장점·활용·섭취·선택·보관 정보인가.
- 확인해서 사용할 수 없는 내용 대신 독자에게 필요한 다른 정보를 충분히 조사했는가.
- 같은 사실을 도입·표·본문·요약에서 반복하지 않았는가.
- 100mL→200mL 같은 단순 산술 확장으로 표를 채우지 않았는가.
- 주의사항이 다른 소제목을 압도하지 않는가.
- 전문용어를 지워도 독자가 핵심 답과 행동 기준을 이해할 수 있는가.
- 강조·사진·내부링크가 실제 독자에게 도움이 되는가.

이 검토는 작성자 편집 검토이며 자동 AI 의미 판정이나 자동 재작성 루프를 만들지 않는다.

## 기술 검사·발행
- `publishing/direct-authoring-contract.mjs`와 `publishing/direct-preflight.mjs`를 사용한다.
- PREFLIGHT_PASS는 구조 검사이며 내용 품질 인증이 아니다.
- 신규는 `target-resolution request → result=new → posts/*.json → publish-posts.yml`.
- 기존 수정은 `updates/direct-*.json → direct-author-update.yml → update-posts.yml`.
- direct source는 `contentStandard=SP1`을 유지한다.
- 실제 제출 시작 뒤 최종 상태가 확인될 때까지 해당 source와 실행 코드를 바꾸지 않는다.
- 원고 저장이나 CI PASS만으로 완료라고 하지 않는다.
- PUBLIC_VERIFIED와 신규 `published` 또는 기존 `updated` 원장을 확인해야 완료다.
