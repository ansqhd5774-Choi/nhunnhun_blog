# 음식 direct/SP1 작성·저장·제출 계약 — 2026-10-12

적용 범위는 `nhunnhun_blog`의 음식 카테고리 신규 및 전체 수정 `direct-* / SP1`이다. 음식의 내용·검색 의도·소제목·문체는 `docs/project-instructions/PROJECT_INSTRUCTIONS_FOOD_R8.1.txt`가 결정한다. 이 계약은 검사·보존·저장·제출 기술만 정하며 다른 카테고리의 편집 구조를 포함하지 않는다.

## 단일 규격과 검사

`publishing/direct-authoring-contract.mjs`가 이미지 허용 키·최소 수·강조 최소 수·핵심 H2 상한을 제공한다. `publishing/direct-preflight.mjs`가 강조·이미지·본문 집중 검사를 호출한다.

- 이미지 최소 3개.
- 대표 이미지·본문 이미지 순서와 alt, 원출처·저작자·라이선스·출처 링크·중복을 확인한다.
- imageReview 허용 키: `src, alt, role, composition, sourcePage, author, license, visualChecked`.
- `visualChecked`는 선택적 boolean 관찰 기록이다. 누락/false 때문에 제출을 막지 않는다. 실제 확인 없이 true를 자동 생성하지 않는다.
- 기존 원고·archive에서 이미지를 재사용할 때 자산·귀속 정보는 재사용할 수 있지만 `visualChecked`는 승계하지 않는다.
- 사용자가 대표 이미지로 부적합하다고 명시한 원출처는 기존 수동 거부 목록과 이미지 검사로 차단한다.
- 강조 하한: strong18·mark8·mark>u>strong2.
- 핵심 H2 최대 6개. FAQ·핵심 정리·자료 출처 등 보조 항목은 제외한다.
- 기존 연구 세부 과다·근거 한계 반복 구조 검사는 유지한다.
- preflight가 FAIL이면 제출하지 않고 작성 단계에서 보완한다.
- PREFLIGHT_PASS는 구조 검사이며 의학적 진실, 문체 품질, 소제목 의미 적합성, 사진 시각 검토 인증이 아니다.

## 쉬운말 작성·저장 전 검토

- 건강·영양 배경지식이 없는 독자가 전문용어를 따로 검색하지 않아도 이해할 수준으로 쓴다.
- 답을 먼저 쓰고 이유와 근거를 뒤에 붙인다.
- 독자 판단에 필요하지 않은 기관 약어·DB 이름·연구 방법명·전문 성분명은 본문에서 빼고 출처에 둔다.
- 전문명이 꼭 필요하면 쉬운 설명을 먼저 쓰고 괄호로 한 번만 보조한다.
- 예: `USDA 자료`→`공식 영양 자료`, `비헴철`→`콩·채소에 든 철분`, `옥살산`→`신장결석과 관련될 수 있는 성분`, `표준화 분말`→`연구에서 사용한 분말`, `메타분석`→`여러 연구를 함께 살펴본 결과`.
- 연구 설계·표본·통계 수치는 결과 해석이나 행동 결정에 필요한 것만 남긴다.
- 저장 전 각 문단에서 전문용어를 지워도 핵심 답과 행동 기준이 유지되는지 확인한다.
- 저장 전 각 핵심 H2를 `음식 축 → 실제 독자 질문 → H2 → 첫 문장 직접 답변`으로 대조한다.
- 이 검토는 작성자 편집 기준이며 새 AI 의미 판정·자동 재작성·분야별 CI를 추가하지 않는다.

## 근거 범위 검토 — 저장 전 필수

- 사람 대상 연구를 인용할 때 **해당 음식 자체인지, 같은 종인지, 같은 부위인지, 같은 제형인지**를 먼저 확인한다. 정제 성분·추출물·오일·보충제·유사 종의 결과를 일반 식사량의 음식 효능으로 바꾸지 않는다.
- 연구 조건이 실제 음식 섭취와 다르면 같은 문단에서 차이를 직접 밝힌다. 특히 `종·부위·제형·용량` 중 하나라도 다르면 독자가 일반 식품 효과로 오해하지 않게 구분한다.
- `항산화·항균·항염`처럼 여러 작용을 한 문장에 묶을 때는 연결된 출처가 **각 주장 모두를 직접 뒷받침하는지** 확인한다. 일부만 뒷받침하면 주장을 분리·삭제하거나 해당 근거를 별도로 연결한다.
- 전통 약재·민간요법·전통지식 자료는 `약용 기록` 또는 `전통 사용 기록`임을 먼저 밝힌다. 이를 일반 음식량의 현대 임상 효능이나 안전성 근거처럼 쓰지 않는다.
- 사람 연구의 표본 수를 쓸 때 전체 모집 인원과 실제 해당 음식·성분 투여군 인원을 구분한다. 전체 참가자를 모두 섭취군처럼 쓰지 않는다.
- 연구에서 사용한 양은 `연구 용량`으로 표시하고 공식 권장량·일상 식용량·제품 표시량과 섞지 않는다.
- 위 항목은 `authoring/prepare-direct-source.mjs`의 `editorialReview`에 항상 노출한다. 이 검토는 작성자 확인용이며 자동 의미 PASS를 생성하지 않는다.

## Gate 0

1. 완성 원고 JSON 전체를 자동 발행 경로 밖에 보존한다.
2. sourceId·articleId·title·전체 source digest·검사 결과·저장/실행 상태를 함께 남긴다.
3. 일반 Chat은 지원하는 파일 첨부·산출물 기능을 사용하며 사용자 PC 로컬 기능을 요구하지 않는다.
4. GitHub 저장 성공은 응답 문구만으로 판정하지 않는다.
5. 실제 커밋 SHA에 고정한 source를 다시 읽고 전체 JSON digest가 일치할 때만 `GITHUB_SOURCE_CONFIRMED`다.
6. 외부 보안 검사가 GitHub 쓰기를 거절하면 `WRITE_BLOCKED`로 기록하고 우회하지 않는다.
7. 파일 부재·조회 제약·내용 불일치를 각각 구분한다.
8. 재개할 때는 같은 source의 저장·원장·실행 상태부터 확인하고 근거 변화가 없으면 조사를 반복하지 않는다.

## 실행·대기열

- 신규: `posts/*.json → publish-posts.yml`.
- 기존 수정: `updates/direct-*.json → direct-author-update.yml → update-posts.yml`.
- 자동 실행이 있으면 해당 실행을 관찰하고 수동 실행을 겹치지 않는다.
- 공통 mutation 잠금과 기존 queue 정책을 유지한다.
- queued·busy·offline·cancelled·failed를 구분한다.
- 실제 제출 시작 후 최종 상태가 확인될 때까지 해당 source와 실행 코드를 변경하지 않는다.

## 공개 검증·복구

- HTTP200·SUBMIT_CLICKED·Actions SUCCESS만으로 완료라고 하지 않는다.
- 해당 source의 `PUBLIC_VERIFIED`와 신규 `published` 또는 기존 `updated` 원장을 확인한다.
- PUBLIC_VERIFIED는 공개 반영·렌더 검증이며 의학적 또는 편집 의미 인증이 아니다.
- submitting 또는 제출 후 상태가 불명확하면 재제출하지 않는다.
- 기존 수정은 `update=false + source_id`, 신규는 `recover-publication + source_id + 확인된 public_url`로 읽기 전용 확인을 수행한다.

## 보존

- 과거 공개 원장과 읽기 전용 복구 상태는 삭제하지 않는다.
- 이 계약을 이유로 기존 공개 글을 자동 재작성하거나 재발행하지 않는다.
- 음식 작성 판단에 다른 카테고리 원고·큐·편집 기준을 사용하지 않는다.
