# direct/SP1 작성·저장·제출 계약 — 2026-10-12

적용 범위는 `nhunnhun_blog`의 신규 및 전체 수정 `direct-* / SP1` 기술 계약이다. 음식의 내용·검색 의도·소제목·문체는 `docs/project-instructions/PROJECT_INSTRUCTIONS_FOOD_R8.1.txt`가 결정하고, 영양소 내용 기준은 `ansqhd5774-Choi/nhunnhun_nutrients`의 최신 `PROJECT_INSTRUCTIONS.txt`가 결정한다. 이 계약은 검사·보존·저장·제출 기술을 정하며 카테고리별 편집 구조를 덮어쓰지 않는다.

## 단일 규격과 검사

`publishing/direct-authoring-contract.mjs`가 이미지 허용 키·최소 수·강조 최소 수·핵심 H2 상한을 제공한다. `publishing/direct-preflight.mjs`가 강조·이미지·본문 집중 검사를 호출한다.

- 이미지 최소 3개.
- 대표 이미지·본문 이미지 순서와 alt, 원출처·저작자·라이선스·출처 링크·중복을 확인한다.
- imageReview 허용 키: `src, alt, role, composition, sourcePage, author, license, visualChecked`.
- `visualChecked`는 선택적 boolean 관찰 기록이다. 누락/false 때문에 제출을 막지 않는다. 실제 확인 없이 true를 자동 생성하지 않는다.
- 기존 원고·archive에서 이미지를 재사용할 때 자산·귀속 정보는 재사용할 수 있지만 `visualChecked`는 승계하지 않는다.
- 사용자가 대표 이미지로 부적합하다고 명시한 원출처는 기존 수동 거부 목록과 이미지 검사로 차단한다.
- 음식 direct/SP1 강조 하한: **strong25·mark12·mark>u>strong8**.
- 영양소 direct/SP1 강조 하한: **strong25·mark14·mark>u>strong8**. 그 외 비음식 카테고리는 공통 기본값 **strong18·mark8·mark>u>strong2**를 유지한다.
- 영양소의 `풍부한 식품 TOP7/TOP5/TOP3` 순위표는 1·2·3위를 해당 H2의 직접 답으로 취급해 시각적으로 강조한다. 1위는 최고강조를 우선하고 2·3위는 최소 mark>strong을 사용하며, 순위 자체는 효능이 아니므로 기본 `info` 톤을 사용한다.
- **음식의 mark·최고강조는 각 핵심 H2가 독자에게 약속한 직접 답을 먼저 드러낸다.** 그중 확인된 긍정적 효능·개선 결과·핵심 성분의 건강상 역할·건강 개선 실천 행동·중요 안전 행동을 최우선으로 한다. 다만 H2 자체가 `제철·맛·식감·먹는 법·고르는 법·보관`처럼 독자가 직접 찾는 음식 정보를 약속하면, 그 질문에 대한 핵심 답도 mark·최고강조 대상으로 사용할 수 있다. `효과 없음`, `미확인`, `공식 권장량 없음`, `연구와 일상 섭취 조건 차이`, `같은 효과로 계산할 수 없음` 같은 한계 설명은 일반 문장 또는 strong으로 둔다. 금기·응급처럼 놓치면 위해가 커지는 행동은 안전 예외로 강하게 강조할 수 있다.
- **강조 하한을 채우기 위해 근거 없는 효능·수치·문장을 만들거나 행정·유통·표시 확인·맛·향 문장을 임의로 승격하지 않는다.** 단, 맛·제철·식감·먹는 법 등이 해당 H2의 직접 답이면 개수 채우기와 무관하게 핵심 정보로 강조할 수 있다. 필요한 경우 근거 조사를 넓혀 실제 건강·영양·안전·섭취·선택 정보를 보강한다.
- 핵심 H2 최대 6개. FAQ·핵심 정리·자료 출처 등 보조 항목은 제외한다.
- 연구 자료는 사실 확인에 사용하되 연구 설계·근거 등급·한계 설명 자체를 독자용 소제목이나 반복 서술의 중심으로 만들지 않는다.
- preflight가 FAIL이면 제출하지 않고 작성 단계에서 보완한다.
- PREFLIGHT_PASS는 구조 검사이며 의학적 진실, 문체 품질, 소제목 의미 적합성, 사진 시각 검토 인증이 아니다.
- `authoring/prepare-direct-source.mjs`는 음식 6개 축을 `foodAxisReview`로 펼쳐 `독자 질문 → 실제 H2 → 첫 답변 → 작성자 확인 질문`을 함께 보여준다.
- `foodAxisReview`는 결정론적 관찰 자료이며 `automatedSemanticVerdict=false`를 유지한다. 새 AI 의미 판정·자동 PASS·자동 재작성에는 사용하지 않는다.
- `coreH2=6` 또는 구조 PASS만으로 `contentReview=PASS`를 판정하지 않는다. 작성자가 카테고리별 지침의 여섯 축을 직접 대조한 뒤 내용 검토를 완료한다.
- 특히 ② 핵심 효능 축은 제목·검색 의도가 효능·건강 효과를 약속하면 H2와 첫 문장이 **건강상 장점·몸에서 하는 역할·실제 섭취 활용**을 직접 답해야 한다. 연구 설계·근거 수준·한계는 작성자 사실 확인에 사용하고 독자 판단에 꼭 필요한 경우에만 짧게 본문에 남긴다.
- `foodAxisReview.balanceReview`는 독자 가치 우선·부정 반복 제한·안전 내용 집중·강조 균형을 위한 작성자 검토 질문을 제공한다. 자동 의미 판정이나 제출 차단용 게이트로 바꾸지 않는다.

## 쉬운말 작성·저장 전 검토

- 건강·영양 배경지식이 없는 독자가 전문용어를 따로 검색하지 않아도 이해할 수준으로 쓴다.
- 답을 먼저 쓰고 이유와 근거를 뒤에 붙인다.
- 독자 판단에 필요하지 않은 기관 약어·DB 이름·연구 방법명·전문 성분명은 본문에서 빼고 출처에 둔다.
- 전문명이 꼭 필요하면 쉬운 설명을 먼저 쓰고 괄호로 한 번만 보조한다.
- 예: `USDA 자료`→`공식 영양 자료`, `비헴철`→`콩·채소에 든 철분`, `옥살산`→`신장결석과 관련될 수 있는 성분`, `표준화 분말`→`연구에서 사용한 분말`, `메타분석`→`여러 연구를 함께 살펴본 결과`.
- 연구 설계·표본·통계 수치는 독자의 행동 결정에 꼭 필요한 경우에만 본문에 남기고, 그렇지 않으면 작성자 확인과 출처에 둔다.
- 저장 전 각 문단에서 전문용어를 지워도 핵심 답과 행동 기준이 유지되는지 확인한다.
- 저장 전 각 핵심 H2를 카테고리별 프로젝트 지침의 축과 대조한다.
- 이 대조는 작성자가 직접 수행한다. H2 수가 맞는지만 확인하고 넘어가지 않는다.
- 이 검토는 작성자 편집 기준이며 새 AI 의미 판정·자동 재작성·분야별 CI를 추가하지 않는다.

## 독자 가치·경고 균형 — 저장 전 필수

- 도입·핵심 요약·①~④는 주제의 정체, 확인된 장점, 영양적 역할, 실제 활용처럼 독자가 얻을 수 있는 가치를 먼저 보여준다. 일반 사용 자체가 즉시 위험하거나 안전 문제가 검색 의도의 중심인 경우가 아니라면 경고를 글의 첫 인상으로 만들지 않는다.
- ② 효능은 **`건강상 장점·몸에서 하는 역할 → 실제 섭취 활용 → 꼭 필요한 주의`** 순서를 기본으로 한다. 없는 효능은 만들지 않되, 연구의 존재 여부·표본·근거 등급을 효능 설명의 중심축으로 삼지 않는다.
- 연구 부족·미확인·근거 수준·연구 조건 차이 같은 작성자 검토 정보는 독자가 행동을 결정하는 데 꼭 필요할 때만 짧게 남기고, 도입·②·③·⑤·FAQ·요약에 반복하지 않는다.
- 독성·고용량·금기·응급 행동은 카테고리별 안전 H2에 모은다. 다른 H2에는 섭취 행동을 결정하는 데 필요한 최소 주의만 남긴다. 즉시 위험 행동을 막아야 하는 주제는 예외로 한다.
- 일반 음식·향신료에 `건강을 위해 많이 먹는 식품이 아니다`, `치료제가 아니다`, `효과를 기대해 먹으면 안 된다` 같은 방어적 상투문구를 자동 삽입하지 않는다. 실제 오해 가능성과 검색 의도가 있을 때만 쓴다.
- strong은 정의·핵심 성분·주요 수치·필요한 한계 설명에도 사용할 수 있다. **mark·최고강조는 각 H2의 직접 답과 실제 건강·영양·안전 가치를 중심으로 배치한다. H2가 제철·맛·식감·먹는 법·고르는 법·보관을 직접 묻는 경우 그 핵심 답도 시각적 중심이 될 수 있다.** 부정·반박·근거 부족 문구를 mark 개수 충족용으로 승격하지 않는다. 실제 금기·응급 행동은 예외적으로 강하게 강조할 수 있다.
- 작성자는 저장 전에 위 항목을 직접 확인하고, 하나라도 충족하지 못하면 사실을 숨기는 대신 중복 경고를 줄이고 안전 내용을 적절한 H2에 모으며 장점·활용 설명을 앞세우는 방식으로 수정한다.

## 근거 사실 확인 — 작성자 내부 확인

- 연구·공식 자료는 **본문의 주장을 사실 확인하기 위한 자료**다. 연구 자체를 독자용 소주제·제목·반복 설명의 중심으로 만들지 않는다.
- 해당 음식과 다른 종·부위·제형·용량, 정제 성분·추출물·오일·보충제 결과를 일반 식사량의 효과로 바꾸지 않는다.
- 전통 약재·민간요법·전통지식 자료는 현대 치료·예방 효과의 직접 근거로 바꾸지 않는다.
- 연구에서 사용한 양과 공식 권장량·일상 식용량·제품 표시량을 섞지 않는다.
- 독자 오해를 막기 위해 차이를 알려야 할 때만 본문에 짧게 설명하고, 연구 방법·표본·근거 등급을 따로 수집해 글의 중심으로 키우지 않는다.
- 위 항목은 작성자 내부 사실 확인용이며 자동 의미 PASS를 생성하지 않는다.

## Gate 0

1. 완성 원고 JSON 전체를 자동 발행 경로 밖에 보존한다.
2. sourceId·articleId·title·전체 source digest·검사 결과·저장/실행 상태를 함께 남긴다.
3. 음식 direct/SP1은 Gate 0 receipt에 당시 `foodAxisReview` 관찰값과 그 안의 `balanceReview` 질문을 함께 보존한다.
4. 관찰값 저장은 의미 인증이 아니다. 작성자 검토의 관찰 증거이며 자동 PASS를 만들지 않는다.
5. 일반 Chat은 지원하는 파일 첨부·산출물 기능을 사용하며 사용자 PC 로컬 기능을 요구하지 않는다.
6. GitHub 저장 성공은 응답 문구만으로 판정하지 않는다.
7. 실제 커밋 SHA에 고정한 source를 다시 읽고 전체 JSON digest가 일치할 때만 `GITHUB_SOURCE_CONFIRMED`다.
8. 외부 보안 검사가 GitHub 쓰기를 거절하면 `WRITE_BLOCKED`로 기록하고 우회하지 않는다.
9. 파일 부재·조회 제약·내용 불일치를 각각 구분한다.
10. 재개할 때는 같은 source의 저장·원장·실행 상태부터 확인하고 근거 변화가 없으면 조사를 반복하지 않는다.

## 신규/기존 source 스키마 분리

- 신규 글 `posts/*.json`과 기존 글 수정 `updates/direct-*.json`은 같은 JSON 스키마가 아니다. 신규 원고 필드를 기존 수정 원고에 그대로 복사하지 않는다.
- 기존 수정 source의 일반 허용 키는 `id`, `articleId`, `targetUrl`, `expectedCurrentTitle`, `title`, `representativeImageUrl`, `imageReview`, `bodyHtml`, `status`, `approved`, `category`, `contentStandard`, `affiliateProducts`다. 실제 기준은 `publishing/update-core.mjs` 한 곳을 원본으로 삼는다.
- `tags`는 기존 수정 source의 허용 키가 아니다. 현재 수정 러너는 기존 티스토리 태그를 변경하지 않고 그대로 보존하므로 `updates/direct-*.json`에 `tags`를 넣지 않는다.
- 태그 자체를 바꾸는 기능이 필요하면 별도 명시 요청과 지원되는 mutation 경로를 먼저 정의한다. 기존 글 전체 최신화 과정에서 임의로 태그 변경 기능을 섞지 않는다.
- 스키마 오류는 기존 `checkUpdateSource()` 한 번으로 판정한다. 같은 내용을 확인하는 별도 게이트나 재검사 루프를 추가하지 않는다.
- 허용되지 않은 키가 있으면 `E_UPDATE_SCHEMA_UNSUPPORTED_KEYS:<키>`로 해당 키를 즉시 표시하고, source를 한 번 수정한 뒤 표준 실행을 이어간다.

## 실행·대기열

- 신규: `posts/*.json → publish-posts.yml`.
- 기존 수정: `updates/direct-*.json → direct-author-update.yml → update-posts.yml`.
- 자동 실행이 있으면 해당 실행을 관찰하고 수동 실행을 겹치지 않는다.
- 공통 mutation 잠금과 기존 queue 정책을 유지한다.
- queued·busy·offline·cancelled·failed를 구분한다.
- 실제 제출 시작 후 최종 상태가 확인될 때까지 해당 source와 실행 코드를 변경하지 않는다.

## 공개 검증·복구

- HTTP200·SUBMIT_CLICKED·Actions SUCCESS만으로 완료라고 하지 않는다.
- 해당 source의 `PUBLIC_VERIFIED`와 신규 `published` 또는 기존 `updated` 원장을 확인한다.
- PUBLIC_VERIFIED는 공개 반영·렌더 검증이며 의학적 또는 편집 의미 인증이 아니다.
- submitting 또는 제출 후 상태가 불명확하면 재제출하지 않는다.
- 기존 수정은 `update=false + source_id`, 신규는 `recover-publication + source_id + 확인된 public_url`로 읽기 전용 확인을 수행한다.

## 보존

- 과거 공개 원장과 읽기 전용 복구 상태는 삭제하지 않는다.
- 이 계약을 이유로 기존 공개 글을 자동 재작성하거나 재발행하지 않는다.
- 각 카테고리의 작성 판단은 해당 카테고리의 최신 프로젝트 지침을 따른다.
