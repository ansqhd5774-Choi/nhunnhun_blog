# Producer R5.4 — 시간 측정·부분 보완·재개

적용 범위: 음식·영양소·약·질병의 기존 URL 수정 Producer. 기존 publish/update 브라우저 러너, 승인·mutex·원장·공개 검증 계약은 변경하지 않는다.

## 실행

GitHub `기존 글 Queue 로컬 Ollama 자동 수정` → Run workflow에서 `dry_run=true`, `article_id`를 지정하면 공개 변경 없이 조사·작성·검토 결과만 artifact에 저장한다. 로컬 명령:

```cmd
node authoring\update-producer.mjs --dry-run --article=327
```

dry-run은 updates/content-reviews/queue-state를 쓰거나 commit/push/dispatch하지 않는다. 실제 처리 요청은 `dry_run=false`이며 기존 운영 승인 조건을 유지한다. schedule/push는 CONTENT_UPDATE_QUEUE_ENABLED가 true인 경우에만 생성한다. 진행 결과가 불명확한 기존 제출은 정책 변경으로 재시도하지 않는다.

## 처리 순서

공개 제목·본문 확인 → 조사 자료 → 공통 core 명세·근거 사전 검사 → 기존 이미지 검토 확인 → 본문 1회 → 오류 절만 최대 1회 보완 → HTML/R1/R4 검사 → 실제 의미 검토 → source/review 승격 → 기존 수정 workflow.

공통 core는 기존 `queue-plan.mjs`와 `DOMAIN_RULES`를 공유한다. TOP 순위·브랜드·시너지·기간별 효과를 채우도록 강제하지 않는다. 확인되지 않은 효능/양은 한계를 설명할 수 있으나 필수 의약품 허가·질병 안전 자료를 우회하지 않는다. sourceId는 R5.4를 사용해 기존 R5.3 문서에 적용된 예외를 새 원고가 이용하지 않는다.

목차와 근거 사전 검사는 구조·자료 조건 검사다. 의학적 의미가 검증됐다는 뜻이 아니다. 작성 모델과 같은 모델의 실제 의미 검토는 same-author로 기록하며 독립 의료 검토로 보고하지 않는다. sourceIds는 모델이 사용한 자료를 명시하고, 존재하지 않는 ID는 차단한다. 검토 PASS를 코드로 일괄 생성하지 않는다. 이미지 PASS는 기존 시각 확인 기록의 계약 재검사이며 새 시각 확인으로 기록하지 않는다.

## 캐시와 재개

로컬 `LOCALAPPDATA/nhunnhun-queue-cache/stages`에 성공한 조사·초안·부분 보완·검토 응답을 원자적으로 저장한다. LOCALAPPDATA가 없으면 generated-drafts 아래를 사용한다. 24시간 TTL이며 입력·모델·코드 정책·의존성 해시 변경 시 재사용하지 않는다. 원자료는 Git에 추가하지 않는다. 통신 실패 응답은 저장하지 않는다. 부분 보완 응답도 범위 및 내용 재검사를 통과해야 사용한다.

절 누락·인용 ID·반복 오류는 해당 절만 보완한다. 강조는 코드가 만든 실제 본문 발췌 후보에서 모델이 ID를 선택하고 코드로 조립한다. 별도의 짧은 선택 호출이며 본문을 다시 쓰거나 강조할 새 문장을 만들지 않는다. 전체 원고 재생성을 위한 반복 루프는 없다. 의미 검토에서 절별 오류가 명확한 경우 남은 1회의 보완을 사용할 수 있다. 제목/요약 오류, 필수 의료 근거 부족, 불명확한 오류 또는 보완 후 재실패는 검토 필요로 중단한다. 보완한 원고를 다시 전체 검토한다.

캐시는 로컬 디스크를 공유하는 동일 PC에서 재개한다. 다른 PC로 checkpoint가 자동 이동한다고 보장하지 않는다. 모델/GPU 성능을 위해 추론은 끄되 모델·양자화·문맥 크기는 실측 없이 일괄 변경하지 않는다.

## 시간과 완료

artifact의 `<articleId>-metrics.json`: 단계별 ms, 실제 요청 수 및 작성/강조 선택/검토 호출 수, 캐시 적중, prompt/output token, load/prompt/generation/total ms 및 decode tokens/s. duration 미제공은 null, 실제 0은 0이다. GPU 메모리 배치 정보는 조회 가능한 모델만 기록한다. 로컬 R5.4 실행 이력에 실패를 포함한 누적 실행 시간을 기록한다. 이전 R5.3 시간 또는 다른 PC 실행 시간까지 포함한 합계로 보고하지 않는다. 순수 생성 시간과 전체 누적 소요 시간을 혼동하지 않는다. 20~30분은 검증 목표이며 SLA 또는 측정된 개선 결과가 아니다.

완료 확인은 consumer workflow 완료 이벤트 및 정기 실행의 시작에서 1회 조회한다. queued/running이면 PENDING을 반환하고 러너를 즉시 반환한다. 소비자 성공·같은 source commit·fingerprint·공개 검증 원장·공개 제목을 확인한 경우에만 DONE을 기록한다. 기존 25분 대기로 한 대의 러너를 점유하지 않는다.

## 검증·복구

새 테스트는 네 분야 core, 근거 부족 조기 차단, 부분 보완 범위/1회 제한, 캐시 변경·TTL·실패, metric 결측·0, 음식 위험 주장, 불확실 제출 재시도 금지, 단일 완료 조회를 검증한다. fixture 성공은 실제 글 품질/발행 성공이 아니다.

실제 테스트는 dry-run 1건 → 내용/근거/시간 확인 → 기존 승인 범위의 수정 1건 → 공개 검증·원장 확인 순서다. 실패 시 generated-drafts 기록과 metrics를 보존하고 전체 원고를 임의 재생성·재제출하지 않는다. 코드 복구는 해당 PR의 변경만 revert하며 기존 글/원장/queue 항목을 일괄 되돌리지 않는다.

출처 검사: 편집 요약을 원문으로 취급하지 않는다. 실제 URL에서 조회한 발췌만 작성에 전달하며 문단별 연결 출처의 원문 구절과 수치를 대조한다.

실제 로컬 검증: 강화 전 75초 dry-run은 출처 불일치가 발견되어 품질 성공으로 인정하지 않았다. 강화 후 dry-run은 의미·출처 검사에서 차단됐다. 동일 품질 기준의 시간 개선과 실제 수정 발행은 아직 미검증이다.
